# Field Report 001 — CSDD v0.1.0 in Real Projects

- Version observed: `v0.1.0`
- Status: completed field observation
- Primary observer: project maintainer
- Projects observed: four
- Evidence type: qualitative real-world usage

## Context

CSDD v0.1.0 was installed and used across four active repositories:

- a travel-agency website;
- a WhatsApp-oriented commerce website;
- an occupational health and safety hub and agent;
- a new website built with Astro.

The projects differed in size, architecture, maturity, and frequency of work.
CSDD was used during normal development rather than through formal evaluation
fixtures.

## Observed Value

The central premise of CSDD held in real usage: agents were ephemeral, while
project state persisted through versioned artifacts.

The primary observed benefits were:

- substantially less repeated explanation between sessions;
- clearer and more stable requirements;
- easier recovery of project context after pauses;
- clearer placement for specifications, decisions, tasks, and resumable state;
- better alignment between the human operator and coding agents;
- lower ambiguity when delegating work;
- useful adaptive hydration rather than unconditional loading of all project
documentation.

The protocol changed the maintainer's normal development workflow rather than
serving only as additional documentation.

## Observed Frictions



### Recently Completed retention

Agents frequently retained more completed tasks than remained operationally
useful.

The phrase "small recently completed window" was not precise enough to produce
consistent compaction behavior.

### Handoff churn

Some agents updated `handoff.md` repeatedly during a single uninterrupted
session.

This caused the handoff to resemble a progress log rather than a resumable
checkpoint. Rapid transitions could leave it temporarily behind repository
reality.

### Non-canonical TODO structures

Agents sometimes introduced new top-level sections such as:

- `Icebox / Deferred`;
- product-wave sections;
- custom categories derived from a prompt or workstream.

Some of these categories expressed useful project concepts, but they mixed task
state with task grouping and escaped the canonical document contract.

### Repeated manual adoption flow

Existing repositories were initialized through prompts asking an agent to
inspect current documentation and translate the relevant project state into a
new `.csdd/` directory.

This workflow was useful across all four repositories, but it was not exposed
as an explicit CSDD operation.

### Claims and Git state could diverge

The largest limitation appeared under parallel work.

A task could be recorded as claimed or completed while the working tree,
commits, branches, or other agents reflected a different execution state.

Observed examples included:

- tasks marked completed while scoped changes remained uncommitted;
- changes landing on `main` while another agent was staging related files;
- multiple tasks modifying shared hot files;
- time spent attributing individual hunks to the responsible task;
- scopes appearing released while related files were still changing.

CSDD described intended coordination state, while Git remained the primary
sensor of observed execution state.

## Collaborating Agent Assessment

An agent that worked extensively with the protocol independently identified the
same central limitation.

Its main recommendations were:

1. add a short pre-edit refresh checkpoint;
2. require repository-relative paths or globs in `Scope`;
3. distinguish code-complete work from landed work;
4. use handoff for transfer boundaries and live collisions rather than progress
  narration;
5. establish a minimal convention connecting task IDs to Git commits.

The agent explicitly recommended against distributed locks or abandoning the
local-first advisory model.

## Product Interpretation

CSDD v0.1.0 successfully models:

- durable project truth;
- explicit operational intention;
- resumable task state;
- human and agent responsibility;
- proportional context hydration.

It models observed Git execution state less strongly.

The working hypothesis for v0.2.0 is:

> CSDD declares coordination intent; Git exposes observed execution state.
> Agents must reconcile both before editing, landing, or closing collaborative
> work.



## Proposed v0.2.0 Priorities

1. Git-aware task lifecycle and refresh checkpoints.
2. Path-based scope contracts and inexpensive collision detection.
3. Separation between implementation completion and Git landing.
4. Canonical TODO states, grouping, and retention.
5. Boundary-driven and collision-oriented handoffs.
6. `/csdd init` for adoption of existing repositories.
7. Evaluation scenarios derived from real concurrency failures.



## Non-goals

The findings do not justify adding:

- distributed locking;
- a background heartbeat service;
- a database;
- automatic commits;
- a replacement for Git;
- additional mandatory CSDD documents.



## Evidence Limitations

This report is qualitative.

The observations came primarily from one maintainer across private or
small-team projects. Harness and model coverage was not controlled, and no
formal timing comparison was performed.

The findings are strong enough to guide design exploration, but they should not
be treated as general performance measurements.
